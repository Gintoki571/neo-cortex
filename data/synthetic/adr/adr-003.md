# ADR-003: Session-cache policy (TTL, eviction, memory)

## Status

Accepted, 2026-06-23.

## Context

INC-01 showed what happens when session-cache runs short of memory. The cluster began evicting live sessions, and users were logged out with no warning and no reason they could see. Eviction was simply picking whatever had been used least recently, so sessions that were still valid were removed alongside the stale ones.

Beatrice pulled the eviction and memory numbers for the incident window, and they made the picture clear enough that we did not need a longer investigation. The settings we ran with were never sized for the number of sessions we now hold.

## Decision

Set the session-cache policy as follows:

- Session time-to-live: 900 seconds.
- Eviction policy: volatile-ttl, so only keys that carry a time-to-live are candidates for eviction, and the ones closest to expiry go first.
- Memory: 8 GB per cluster.

## Consequences

- Live sessions are far less likely to be evicted under memory pressure, because eviction now prefers keys that are already close to expiring.
- Memory alarms fire earlier, which gives on-call time to act before users notice.
- A user who stops using the dashboard for 15 minutes will be signed out.
- Capacity planning for session-cache now starts from 8 GB rather than the old figure.
- Noor will check the eviction and memory figures again after the first full month on these settings, and the result will be noted against this record.
