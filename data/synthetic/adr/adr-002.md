# ADR-002: Transactional outbox for ledger events

## Status

Accepted, 2026-06-09.

## Context

ledger-service writes each double-entry posting to its own database, and then the rest of the platform has to hear about it. Today those are two separate steps. A crash between them can leave the ledger and the event stream disagreeing: a posting that exists in the ledger but never reached anyone downstream, or the reverse. I raised this while reviewing the failure modes of the payment path, and nobody on the review could show me that the two steps would stay in step under retries.

Events carry the transaction id, so that consumers can match them back to ledger rows. We have never written down exactly how that id is shaped in events, which is a gap I am not closing in this record.

## Decision

ledger-service writes each event into an outbox table in the same database transaction as the posting. A separate publisher reads committed rows from the outbox and sends them to event-pipeline, which is the broker. The publisher is the piece I wrote, and it becomes the only path by which ledger events reach the bus.

## Consequences

- A ledger write and its event can no longer disagree after a crash; the publisher catches up when it restarts.
- Events reach consumers slightly after the posting itself, not in the same instant.
- The publisher retries, so consumers have to tolerate a message that arrives more than once.
- The outbox table needs monitoring. A growing backlog is the first sign that the publisher cannot reach the broker.
