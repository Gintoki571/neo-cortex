# ADR-007: Lower session idle TTL to 300 seconds

## Status

Accepted, 2026-08-12. Supersedes the TTL value in ADR-003 (the 900 s figure); the rest of ADR-003 stands.

## Context

Our SOC 2 Type II audit, run by Ashgrove Assurance, produced finding AF-12: sessions on payment-capable accounts stay valid for longer than 5 minutes when idle. Our idle limit is currently 900 seconds. The auditors consider anything above 300 seconds an exception that needs compensating controls we do not have.

I wrote the token introspection endpoint in auth-service, so I looked at what a shorter TTL would cost: clients already refresh sessions on activity (sliding expiry), so a 300 second idle limit mostly affects people who walk away from the dashboard. It also lowers session-cache memory pressure.

For clarity, two unrelated numbers that look similar: audit-log retention is 900 days, and the web-dashboard HTTP client timeout is not touched by this change.

## Decision

Set `session.ttl_seconds` from 900 to 300 in production, effective immediately on 2026-08-12. Keep sliding expiry. No per-customer overrides.

## Consequences

- Users idle for more than five minutes will see the login page; support has a canned reply ready.
- Lower steady-state memory in session-cache.
- AF-12 can be closed at the next audit checkpoint.
